## Building and running on macOS

One-time setup: Xcode Command Line Tools, Homebrew, then:

```bash
brew install clang-format cmake pkg-config meson nasm yasm
tools/macOS_dependencies_setup.sh
tools/macOS_dependencies_build.sh
```

Build, bundle and launch:

```bash
cmake . && make -j8 && cmake --install . --prefix "$PWD/dist/games247.app/Contents/Resources" && open dist/games247.app
```

Always run it from the `.app` bundle. Run as a bare `./games247` binary, it has no Info.plist, and macOS kills it when it checks Bluetooth status.

## Built-in player (beta)

games247 can run RetroArch's emulator cores (libretro cores) inside its own window instead of launching RetroArch.

**How it works**
- When a game's launch command is a RetroArch command (`RetroArch -L <core> <rom>`), games247 loads that same core itself (`es-app/src/guis/GuiLibretroPlayer.cpp`, hooked in `FileData::launchGame()`).
- If the core can't run in the built-in player, games247 falls back to launching RetroArch as before. That includes cores that need Direct3D, Vulkan on a computer without it, and multi-disc subsystem content.
- **GPU cores** (OpenGL, for example Mupen64Plus-Next for the N64) get their own OpenGL context on games247's window, as in RetroArch, so they can't disturb games247's drawing. The context is the kind the core asks for: a core profile context for modern OpenGL, or a compatibility profile one for older OpenGL (the Windows build of Mupen64Plus-Next asks for this; `LibretroCore::createHWContext`). They draw into a framebuffer that games247 creates; each frame is copied back and shown like a software core's, so screen modes, the CRT filter and the pause menu all work (`LibretroCore::acceptHardwareRender`, `createHWFramebuffer`, `readHWFrame`).
- **Vulkan cores** (for example Xenia Edge for the Xbox 360) draw on a Vulkan device of their own (`es-app/src/libretro/LibretroVulkan.cpp`). The Vulkan loader is opened at run time (`vulkan-1.dll` on Windows), so games247 still starts on a computer without Vulkan, and only Vulkan cores then fall back to RetroArch. Cores with a context negotiation interface (v1 or v2) create the instance and device themselves through games247's wrappers, which add the extensions it needs (portability enumeration and subset for MoltenVK); otherwise games247 creates them, on a separate graphics card if there is one. Each picture the core hands over with `set_image` is copied into memory and shown like a software core's (`LibretroVulkan::collectFrame`). The copy is started after `retro_run` returns, not inside the video callback, because cores like xemu draw on threads of their own that can still need the core's locks while the callback runs; games247 waits at most 50 ms for it and otherwise picks it up the next frame (a picture that comes while a copy is still going is skipped, its semaphores still passed on). A copy still not done after 5 seconds is logged. The command buffer and fence are only reused once the GPU is done with them: 8-bit and 10-bit RGBA/BGRA formats are converted on the CPU, other formats are blitted to BGRA8888 on the GPU first. The player keeps one frame in flight (sync index mask 1). Duped frames still signal the core's signal semaphore, and command buffers passed with `set_command_buffers` are submitted with the copy. Tested on macOS (Apple M4, MoltenVK from Homebrew: `brew install molten-vk vulkan-loader`) with a small test core: both negotiation and games247's own device, semaphores and core command buffers, RGBA8, BGRA8, A2B10G10R10 and RGBA16F pictures, and quitting from the pause menu. The Khronos headers (Apache-2.0 or MIT) are in `es-app/src/libretro/vulkan/include`, `libretro_vulkan.h` (MIT) next to `libretro.h`.
- **Xbox 360**: Xenia Edge's libretro core (`xenia_edge_libretro.dll`, Windows and Linux only; there's no macOS build on libretro's build server) is the first Xbox 360 command, so it's downloaded and run in the built-in player like any other core. It draws with Vulkan (`xenia_graphics_api = "vulkan"`, as the player can't do Direct3D 12), needs no BIOS, and takes `.iso`, `.xex`, `.zar`, `.xcp` and `.m3u`. Save states aren't supported by the core; games save to the emulated console's storage in `bios/Xenia-Edge/content`. The standalone Xenia commands are still there as alternatives. **Not tested yet**: the core itself, which needs Windows (or Linux) with a Vulkan 1.1 graphics card and a CPU with AVX.
- **Original Xbox**: xemu's libretro core (`xemu_libretro.dll`, Windows and Linux only) is the first Xbox command; games247 sets `xemu_renderer = "opengl"` in `resources/libretro/xemu_libretro.opt` (the core itself defaults to Vulkan; on macOS it always uses OpenGL). On Windows with an AMD Radeon 890M, the whole games247 window stopped updating as soon as the core created its Vulkan device: the launch screen stayed up, while the main loop, input, cloud check, emulation and sound carried on. Nothing in games247's OpenGL state changes then (Vulkan pictures are copied through memory), and other Vulkan cores haven't been seen doing it, so the cause is unknown, possibly the driver with a borderless full-screen OpenGL window; the core's OpenGL renderer avoids it. The OpenGL renderer asks for an OpenGL 4.0 core context, which games247 creates as for other GPU cores. It needs three files in `bios/xemu`: the MCPX boot ROM `mcpx_1.0.bin` (512 bytes), the flash BIOS `Complex_4627v1.03.bin` (256 KB or 1 MB; `Complex_4627.bin` also works) and a hard disk image `xbox_hdd.qcow2`. Before the core starts (`XboxBios`), boot ROMs and BIOSes under other names, in `bios/xemu` or straight in `bios`, are spotted by name and size and copied to those names (names with `mcpx`, or with `complex`, `4627` or `xbox`; EEPROM, Chihiro and HDD files are skipped). If any are still missing, matching files in the FTP storage's `bios` folder are offered for download as with other systems. The hard disk is xemu's own blank, copyright-free image, downloaded from GitHub (`xemu-project/xemu-hdd-image`, a 68 KB zip) and unzipped when it's the only file missing. The EEPROM is made by the core. Games are XISO images (`.iso`/`.xiso`; Redump ISOs need converting with extract-xiso). ParaLLEl Xbox's core isn't on libretro's build server, so only xemu is set up, but it's recognised the same way. The option file also sets `xemu_vk_fast_paths = "none"` for anyone who turns Vulkan back on: the core's own description says the fast paths are broken on AMD, and on a Radeon 890M the picture stopped on the game's first screens while the sound went on (cores from before 16 November 2026 turn them all on by default, later ones only off on AMD; games247 doesn't update a core it has downloaded). **Tested** on macOS with a Vulkan test core standing in for xemu: a BIOS and boot ROM under other names in the bios folder were copied to `bios/xemu`, and the hard disk image was downloaded, unpacked and the core started. **Not tested yet**: the real core (Windows/Linux only).
- **Arcade clones**: `resources/MAME/mamenames.xml` has a `<cloneof>` entry for each clone, naming its parent set (27,644 of them, from MAME 0.289's driver file; `tools/mame_create_index_files.sh` writes them too). `MameNames::getParent()` reads them. In the game lists of arcade and Neo Geo systems, each folder's sets are grouped by parent set (`FileData::groupVersions()`, run whenever a folder is sorted or counted): the parent set is shown, or the clone first by name when the parent isn't there, and the others are flagged as other versions. They stay in the folder, so their metadata is saved as before, but `getChildrenListToDisplay()`, the game counts and `getFilesRecursive(displayedOnly)` (random game, screensaver) leave them out. Collections (favourites, last played, all games and so on) are unaffected. Starting a grouped game (`GamelistBase::launchOrPickVersion`) opens a CHOOSE A VERSION list with every version's full MAME name, the shown one first; the chosen set is launched as usual. The setting `ArcadeGroupClones` (Other Settings > Show arcade clones as one game, on by default) turns the grouping off. **Tested** on macOS with seven made-up MAME sets: four entries and a count of 4, the version list, launching `sf2ua` from it (its play count saved in the game list), and the setting off showing all seven.
- **Regional versions** (other systems): the same grouping works by file name (`FileData::versionKey()`). Round-bracket tags that only name regions or languages (No-Intro and GoodTools codes: `(E)`, `(USA, Europe)`, `(En,Fr)`, `(M3)`) or a revision (`(Rev 1)`, `(v1.1)`), and every square-bracket tag (`[!]`, `[b1]`, `[T+Eng]`), are left out and case is ignored (`gameWithoutVersionTags()` in `es-app/src/libretro/GameRegion.cpp`); other tags such as `(Disc 1)`, `(Beta)`, `(Proto)` or `(Demo)` are kept, so those stay separate entries. The version shown is the one for the player's region (`versionPreference()`: Europe first, or USA for American English, Canadian, Mexican Spanish and Brazilian Portuguese, Japan for Japanese; then World releases, the next region, any other region, untagged names), with square-bracket tags other than `[!]` last, then first by name. The version list shows the file names, as scraped names are the same for every version. Setting `GroupRegionalVersions` (Other Settings > Show regional versions as one game, on by default). **Tested** on macOS with nine made-up Master System files: seven entries (three Sonic versions as one, two Alex Kidd versions as one, both Phantasy Star discs and Wonder Boy (Proto) apart) and the version list.
- **N64 and Saturn border crop**: N64 and Saturn games often draw inside a black border that differs from game to game. For N64 cores (Mupen64Plus-Next, ParaLLEl N64) Saturn cores (Beetle Saturn, Kronos, Yabause, YabaSanshiro) and LRPS2 the player looks at every sixth frame and crops off any edge that has stayed black since the game started (`GuiLibretroPlayer::updateAutoCrop`). The area kept only grows, so nothing the game draws is cut off, and black frames (fades, loading screens) are ignored. An edge is only cropped once the game fills at least 70% of the frame that way, so a small logo at the start isn't zoomed in on. The picture keeps its pixel shape, so the aspect ratio follows the crop.
- **Amiga Kickstart**: each Amiga model needs its Kickstart ROM in the bios folder (`kick40068.A1200`, `kick40063.A600`, `kick37175.A500`, `kick34005.A500`, CD32: `kick40060.CD32` and `kick40060.CD32.ext`). The bios folder is `<games247 folder>/bios` (`C:\Users\<name>\.games247\bios` on Windows), or RetroArch's `system` folder on a Mac that has RetroArch. Before an Amiga game starts (`AmigaKickstart`, `GuiLibretroPlayer::nextPreStartStep`), ROMs there under other names are recognised by their CRC32 (from UAE's ROM list) and copied to the name PUAE looks for; Amiga Forever's encrypted ROMs are decoded with its `rom.key`, and a 256 KB ROM saved twice over as 512 KB is cut to size. If the model's Kickstart is still missing and the FTP storage has a `bios` folder with Kickstart-like files (`kick*`, `amiga-os*`, `*.rom`, `rom.key`...), the player offers to download them; otherwise, or when declined, the game starts with AROS (the free Kickstart replacement in the core) and a popup names the missing file.
- **Atari ST TOS**: the Atari ST core (Hatari) only starts with a TOS ROM named `tos.img` in the bios folder. Before an Atari ST game starts (`AtariTos`, `GuiLibretroPlayer::nextPreStartStep`), a TOS ROM there under another name (a `.img`/`.rom`/`.bin` file with "tos" in its name, 192/256/512/1024 KB, starting with a BRA instruction) is copied to `tos.img`. If there's still none and the FTP storage's `bios` folder has TOS-like files, the player offers to download them (EmuTOS images such as `etos192uk.img` work too); otherwise the game doesn't start and a popup says where to put `tos.img` (RetroArch can't help without it either, so there's no fallback to it). Hatari B, which has EmuTOS built in, skips the check.
- **PlayStation BIOS**: Beetle PSX (the first PlayStation command) looks in the bios folder for the BIOS of the game's region, `scph5501.bin` (USA), `scph5502.bin` (Europe) or `scph5500.bin` (Japan), and starts with its built-in OpenBIOS when it's missing, which some games don't work with. Before a PlayStation game starts (`PsxBios`), BIOS files there under other names are recognised by their MD5 (from DuckStation's list of known BIOSes) and copied to the name for their region: the v3.0 BIOS the core asks for first, otherwise another version of the same region (Beetle runs it with a warning in its log). The game's region comes from its file name ("(Europe)", "(USA)", "(Japan)"...); without one, any of the three will do. If it's still missing, BIOS-like files in the FTP storage's `bios` folder (`scph*`, `psx*`, `ps1*`, `ps-*`...) are offered for download; otherwise, or when declined, the game starts with OpenBIOS and a popup names the missing file. **Tested** on macOS with the Beetle PSX core: the FTP offer, the download (from a subfolder too) and the OpenBIOS choice. **Not tested**: recognising a real BIOS by its checksum (no real BIOS here).
- **Saturn BIOS**: Beetle Saturn (the first Saturn command) loads `mpr-17933.bin` (USA and Europe) or `sega_101.bin` (Japan) from the bios folder, picked by the disc's region, and can't start without it. Before a Saturn game starts (`SaturnBios`), BIOS files there under other names are recognised by their MD5 (libretro's BIOS list; the Japanese v1.00 also stands in for `sega_101.bin`) and copied to those names. The game's region comes from its file name as for the PlayStation (`GameRegion`); without one, either file will do. If it's still missing, BIOS-like files in the FTP storage's `bios` folder (`*saturn*`, `sega_10*`, `mpr-179*`) are offered for download; otherwise the player says which file is missing. **Not tested**: a real Saturn BIOS and game.
- **PlayStation 2**: LRPS2 (`pcsx2_libretro`) is the first PS2 command on Windows, macOS and Linux (PCEE2 moved to second). It draws with OpenGL (`resources/libretro/pcsx2_libretro.opt`: `pcsx2_renderer = "OpenGL"`, as the player can't do Direct3D); its own defaults of native resolution and fast boot are kept. The core looks for a BIOS of 4 to 8 MB under any name in `bios/pcsx2/bios` and can't start without one. Before a PS2 game starts (`Ps2Bios`), PS2 BIOS files straight in `bios` (recognised by the RESET, ROMDIR and ROMVER entries of their ROM directory) are copied there. If there's still none, BIOS-like files in the FTP storage's `bios` folder are offered for download: names with `ps2`, or SCPH/DTL-H model numbers of five digits, which leaves out PS1 ones like `scph5502.bin`. **Tested** on macOS with LRPS2 and a made-up BIOS: the core download, the FTP offer and download from a subfolder, the copy to `pcsx2/bios` and the core finding it. The core can't draw on macOS (its OpenGL renderer needs GL_ARB_shading_language_420pack, which macOS's OpenGL 4.1 lacks, and its Vulkan renderer crashes when it can't find a `libvulkan.dylib` of its own), so no picture there. **Not tested**: a real BIOS and game on Windows.
- **System ROMs on the FTP storage**: when a system's ROMs are missing, the player lists the FTP storage's `bios` folder there and then (`FtpStorage::listBiosFolder`, with a "CHECKING FTP STORAGE..." panel that B skips), rather than using the listing saved at startup, so files uploaded since games247 started are seen. Folders inside it are listed one level down (such as `bios/xemu`), and files from them are saved straight in the local bios folder, where each system's ROM check finds them.
- **Core options without a default**: like RetroArch, an option the core declares without a default starts at its first value. PUAE declares its Kickstart option that way, and an empty value made it look for a Kickstart with no name (grey screen).
- **LCD filter for handhelds**: handheld systems (Game Boy, Game Boy Color and Advance, Game Gear, Lynx, Neo Geo Pocket (Color), WonderSwan (Color), Pokémon Mini, Supervision, Gamate, Game Master, Mega Duck, Game.com, DS, 3DS, PSP, Vita, N-Gage, Game & Watch) get an LCD filter instead of the CRT one (`resources/shaders/glsl/lcd.glsl`, `Renderer::Shader::LCD`). It has its own setting (`PlayerLCDFilter`, on by default), and the pause menu's filter entry reads *LCD filter* for these systems. Each game pixel is drawn as a sharp LCD cell with antialiased edges, so non-integer sizes don't shimmer. A thin grid separates the cells and fades out when they're under about 4 screen pixels. Colour screens also show RGB subpixel stripes from about 6 screen pixels per game pixel (e.g. a Game Boy on a 1080p screen), but black and white screens (Game Boy, Neo Geo Pocket, WonderSwan and others) don't. The colours follow each console's screen: Game Boy Advance (dark and washed out, which the games were made bright to make up for), Game Boy Color, DS, and a slight desaturation with grey blacks for the early colour LCDs (Game Gear, Lynx, NGPC, WonderSwan Color). Older screens (everything but the DS, 3DS, PSP, Vita, N-Gage and Game & Watch) also get LCD ghosting: each pixel moves 60% of the way to its new colour per frame (`GuiLibretroPlayer::addGhosting`), so sprites that games flicker on alternate frames look see-through, as on the real thing. The Super Game Boy (`sgb`) keeps the CRT filter. **Tested** by rendering the shader offscreen at 2.5x, 4.5x, 5x and 7.5x with each colour profile. Also tested in the app with Genesis Plus GX on a Game Gear game: the filter is picked for the system, the pause menu reads *LCD filter*, and switching it off and on works. **Not tested yet**: a real Game Boy or GBA game, and how the ghosting looks.
- **Errors**: if the built-in player can't run a game and RetroArch isn't installed either, the error shown is the built-in player's reason rather than "couldn't find emulator RetroArch".
- **Analog sticks**: both sticks are passed to cores that read them (N64 and similar). For those cores the left stick no longer also acts as the D-pad.
- The core loader is `es-app/src/libretro/LibretroCore.cpp`. It uses `libretro.h`, the MIT-licensed libretro API header, and no RetroArch code.
- RetroArch doesn't need to be installed. The first time a system needs a core, games247 downloads it from libretro's build server (`buildbot.libretro.com`) into `~/.games247/cores`. On macOS, cores already installed in RetroArch are reused.
- BIOS files go in `~/.games247/bios`. On macOS, RetroArch's `system` folder is used if it exists. Battery saves go to `~/.games247/saves`.
- Turn it on or off in **Main menu → Other settings → Play RetroArch cores inside games247 (beta)**. It's on by default.

**Controls**
- Keyboard (RetroArch's default layout): arrows = D-pad, Z = B, X = A, A = Y, S = X, Q/W = L/R, Enter = Start, Right Shift = Select. Computer cores (C64, Amiga and others) also get the full keyboard.
- Controllers use your games247 controller mapping. The first controller to press a button is player 1.
- Pause menu: **View + Menu** (Back + Start) together on a controller, or **Escape**. It has Resume, Save state, Load state, Screen, CRT filter, Restart game and Quit game. Save states are stored in `~/.games247/saves`.
- Screen options (press A, or left/right, on the entry): **Fit to screen** keeps the game's shape, **Stretch to screen** fills the whole display, **Pixel perfect** scales by whole numbers so every game pixel is the same size. **CRT filter** adds scanlines, a phosphor mask and a slight glow to a flat picture that fills the same area as without it (`resources/shaders/glsl/crt.glsl`, games247's own shader). Both choices are remembered for all games.
- Zipped and 7z games: cores that can't open archives themselves (for example Genesis Plus GX for Master System and Mega Drive) get the game unpacked to `<games247 folder>/tmp/player_content` first, as RetroArch does. The folder is cleared when the game closes. As in RetroArch, only cores that set `block_extract` (VICE, PUAE) get the archive itself: Caprice32 lists zip among its file types but can't open one, and given a zip it booted to BASIC without the game.
- Core options: games247's own defaults live in `resources/libretro/<core>.opt` (RetroArch format, `key = "value"`). A file with the same name in `<games247 folder>/cores/options/` overrides them. The C64 (VICE) layout, by Xbox label: A fire, B joystick up, Y space bar, X swaps the joystick between port 2 and port 1. VICE also crops the C64 borders automatically (`vice_crop = "auto"`). The ZX Spectrum (Fuse) uses the same layout: A fire, B joystick up, Y space bar, and X switches the joystick type (Kempston, Sinclair 1, Sinclair 2, Cursor; Spectrum games each support some of these), with a popup naming the new type. Fuse draws the full border and the player crops it to the 256x192 screen (`games247_crop_size`). While a tape loads, the coloured stripes in the border are spotted (many colour changes down the left border) and the border slides back in, then out again two seconds after it goes still (`games247_border_while_loading`, `GuiLibretroPlayer::checkBorderBusy`). Each time a tape game starts (ZX Spectrum and Amstrad CPC), the player asks for **Fast Load** (selected) or **Real Speed Load**, with the stripes and sounds of the real machine. The core is only loaded once the choice is made, and the choice is passed to it as an option for that game (`games247_load_choice_*` in the option files, `LibretroCore::setOptionOverride`). It's asked for tape files (Spectrum .tap/.tzx/.pzx/.csw, CPC .cdt/.tzx/.voc), including tapes inside a zip, whose file list is read directly (`zipFileNames`); disks and snapshots start straight away. B goes back to the game list. A user option file can set `games247_load_choice_option = ""` to skip the question. The Amstrad CPC (Caprice32) has the same layout too: A fire, B joystick up, Y space bar, RB fire 2, Start Enter, and X switches between the joystick, QAOP keys and Incentive keys, with a popup (`games247_cycle_option` / `_values` / `_labels` cycle any core option this way when the core has no controller types to cycle; the core sees the change live through GET_VARIABLE_UPDATE). The core's per-game key database is off so it can't replace the layout. The player crops the CPC's 640x200 screen out of the core's 768x272 frame (`games247_crop_size` also takes `WxH+X+Y` for a crop that isn't centred), brings the border back while tape loading stripes run, and tapes get the same Fast Load / Real Speed Load choice (`cap32_tape_fastload`). The Amiga (PUAE) also has the C64 layout: A fire, B joystick up (`puae_retropad_options = "jump"`), Y space bar, and X second fire (`puae_mapper_y = "JOYSTICK_2ND_FIRE"`; Amiga games never need the joystick port switched, unlike the C64); Back opens the core's on-screen keyboard and LT/RT are the mouse buttons. The core crops the border itself (`puae_crop = "auto"`). Each floppy or hard drive game asks which Amiga to emulate first: Amiga 1200 (selected), 600, 500+ or 500; CD32 discs start straight away. The Atari ST (Hatari) has the same layout: A fire, B joystick up, Y space bar (Hatari's second button with `hatari_joystick_jump_fire2 = "disabled"`), X autofire (the ST joystick has one fire button), and Back the core's on-screen keyboard (`hatari_vkbd_button = "select"`). Hatari's floppy drive noise (a synthetic click on a loop, unlike PUAE's recordings) is off (`hatari_floppy_sound = "disabled"`).
- Button layouts for cores that can't remap the controller themselves: `games247_button_<button> = "<button>"` in a `.opt` file makes a RetroPad button act as another one (or `none`, or `next_controller`), and `games247_controller_types = "A|B|C"` picks port 1's controller type by the core's names and lists what `next_controller` goes through (`LibretroCore::setupButtonMap`, `applyButtonMap`).

**Tested** (macOS, Apple Silicon): VICE x64sc C64 core with two .prg games. Video and aspect ratio, keyboard joystick input (including taps shorter than a frame), PAL 50 Hz timing (measured 50.03–50.23 fps against a 50.12 target), steady audio buffering, exit, and relaunching in the same session.

**Not tested yet**: game controllers (including the analog sticks), the RetroArch fallback, and a commercial N64 game with the GLideN64 renderer. The GPU path was tested on macOS with a small OpenGL test core and with Mupen64Plus-Next running test programs.

**Not built yet**: a core options menu, rewind and fast-forward.

**Licensing**: cores keep their own licenses. Loading cores that the user installed is fine. If games247 ever bundles cores, check each one: several (Genesis Plus GX, the original Snes9x core and the older MAME versions) forbid commercial use.

## FTP storage

Games can be kept on an FTP server instead of (or as well as) the local ROM folder. The FTP folder holds one folder per system, named like the local ones (`c64`, `amiga`, `nes`, `snes`...).

- **Settings**: *Main menu > FTP storage* has an on/off switch, the address (`ftp.example.com`, `192.168.1.10:2121`, `ftp://...` or `ftps://...`), username, password (masked), path, *Accept self-signed certificates* (for home NAS boxes using FTPS) and *Test connection*. Saving changes reloads the game lists. The password is saved in plain text in `es_settings.xml`, like the scraper password.
- **Listing**: each time the systems load, games247 lists the FTP folder's system folders and the games in each (`FtpStorage::refresh`, called from `SystemData::loadConfig`). Games with a matching file extension that aren't on this computer are added to the game list next to the local games (`SystemData::addFtpGames`). If the server has games for a system that has no local folder, the folder is created so the system shows up. Their gamelist.xml entries (scraped data, favourites) are kept even though the file isn't local yet.
- **Saved listing**: the listing is saved in `ftp_cache.txt` in the games247 folder, with the server, username and path it belongs to. On the next start the saved listing is used straight away, so startup doesn't wait for the server, and the server is checked in the background on its own thread (`FtpStorage::startBackgroundCheck`). One connection is reused for every folder. When the check finishes and something has changed, the new listing is saved and new games are added to the open game lists, the "all games" collection and the system view's game count (`SystemData::addNewFtpGames`, called from `ViewController::update` once no menu, popup or game is open), with a popup saying how many. A folder for a system that isn't loaded yet shows after a restart. Games removed from the server stay in the list until the next start (downloading one says it's not found). If the check fails, the saved listing is kept. The first start, or a change of server, username or path, lists the server straight away as before.
- **Paths** can be typed with backslashes (`\Games\ROMs`) as well as slashes.
- **Cloud symbol**: in the game list, games that are only on the FTP server have a cloud (Font Awesome `\uf0c2`, `ViewController::CLOUD_CHAR`) before their name, or `~` when the theme uses ASCII indicators (`GamelistBase::populateList`). The list is refreshed after a download, so the cloud goes away.
- **Launching**: picking an FTP game shows a download screen with a progress bar (`GuiFtpDownloader`); B cancels. The game is downloaded to `<ROM folder>/<system>/<file>.part`, renamed when complete, and then launched the normal way. From then on it's an ordinary local game.
- **Connection**: libcurl. FTPS is used when the server offers it, otherwise plain FTP. Servers that take a while to wake up (a sleeping NAS, for example) get a 20 second connection timeout and 30 seconds to answer. If the server can't be reached, or a download breaks off, games247 tries twice more, after 3 and then 5 seconds (`RETRY_DELAYS`); a wrong password or a missing file isn't retried. B still cancels a download while it waits. If the server still can't be reached, games247 starts with the local games only.
- Only the top level of each system folder is listed (no subfolders). Games aren't removed from the computer when they're removed from the server.
- **Cloud saves** (`es-app/src/CloudSaves.cpp`, *Main menu > FTP storage > Cloud saves*, on by default): save states and game saves (save RAM) of games in the built-in player follow the player between computers. On the server they're in `saves/<system folder>/<game>.state` and `<game>.srm`, named after the game file. When a game is quit, its state is saved to the game's state slot (the same one as *Save state* in the pause menu) and both files are uploaded in the background. games247 waits up to 30 seconds for an upload when it quits. When a game is launched, the core loads it and then, before the first frame, the server is checked (the player shows *Cloud saves: Checking...*; B skips the check for this game). A game save that's changed on the server is downloaded and written into the core's memory, as RetroArch loads save RAM. If there's a save state on the server, the player asks **Resume from cloud save** or **Start new game**; resuming downloads it if it's changed and loads it. B goes back to the game list. `cloud_saves.txt` in the games247 folder records each file's size and time on the server as of this computer's last upload or download, so files are only downloaded when another computer has changed them. A server that doesn't report file times (MDTM) has its files downloaded every time. Uploads only happen after a successful check, so a computer that couldn't reach the server (or failed to download the cloud save) never replaces a newer save on it. Two computers playing the same game at once: the last one to quit wins. Checking after the core has loaded means a core that can't run in the built-in player still falls back to RetroArch. **Tested** on macOS against a local test FTP server, with a test program calling `CloudSaves` directly: upload, our own upload not counted as new, downloads after another computer's upload, a missing local state, and an unreachable server. Also tested in the app with the Master System core and the local server: the check, the state saved and uploaded on quit, the prompt with *Resume from cloud save* (downloading a state missing locally, then loading it) and *Start new game*. **Not tested yet**: a real FTP server, and a game save (save RAM) coming down from the server in the app.

**Tested** on macOS against a local test FTP server: listing, merging with local games, a system that only exists on the server, download with progress, cancel, launch in the built-in player, Test connection, and starting with the server down. **Not tested yet**: a real FTPS server, Windows.

## Neon theme and transitions

- **Neon** (`themes/neon-247`) is the only theme. The other ES-DE themes aren't installed, and the theme options (theme, variant, colour scheme, font size, aspect ratio, transitions, language, variant triggers and the theme downloader) are gone from *UI Settings*. Saved theme settings from older releases are ignored (`Settings::loadFile`). It's a synthwave design: a dusk sky with a striped sun, neon mountains and an animated grid floor. In the game list the selected game plays on a retro TV, with colour bars when there's no screenshot. System logos, console pictures and system information in `themes/neon-247/system` come from Linear (MIT). The artwork is generated by `tools/neon-theme/`. Font: Orbitron (OFL).
- **Transitions**: scrolling between consoles or game lists is instant (no fade to black). Going between the console carousel and a game list uses the CRT transition below.
- **GIF animations**: a GIF is decoded once and its frames are shared by every element playing it (`GIFAnimComponent::loadFrameCache`, up to 96 MB per animation). Upstream decodes every frame again each time it's drawn, which made the menus stutter with Neon's floor in every system.
- **Neon menus**: every menu, popup and dialog uses the Neon colours (`ViewController::setMenuColors`; the dark/light colour scheme option is gone). Panels are a dark purple gradient with a pink-to-cyan neon edge and a soft glow (`BackgroundComponent::renderNeonPanel`, also used by the built-in player's pause menu), and the selected row is a translucent pink-to-cyan bar. Titles use Orbitron, other menu text uses Rajdhani (OFL, `FONT_PATH_*` in `Font.h`).
- **Background music**: tracks in `resources/music` (and any the user puts in `<games247 folder>/music`) play in random order in the menus (`MusicManager`, decoded with FFmpeg and mixed by `AudioManager`). The music fades out over 1.2 seconds when a game starts, comes back when it ends, and plays quieter while a video has sound. *Sound settings* has an on/off switch and a volume slider. Bundled: five Ocean Software loader tunes, supplied by the project owner.
- **CRT transitions**: a theme can set `<fadeStyle>crt</fadeStyle>` in `capabilities.xml`. Fade transitions between views are then drawn as an old TV switching channels: the picture squeezes into a glowing line, then a dot (`ViewController::renderCRTTransition`). Fades within the system view keep their normal look.
- **Launch screen**: the "Launching game" dialog is replaced by a full-screen loading screen for all themes (`GuiLaunchScreen`). The screen darkens over scanlines, a neon line sweeps out, the marquee and game name fade in with a glow, and NOW LOADING (Monoton font, OFL) blinks below.

## Windows releases and auto-update

**Builds**: every push to the `games247` branch runs the "Windows build" workflow on GitHub Actions. It produces a test installer you can download from the run's page (Artifacts → `games247-windows-installer`).

**Releasing a version**: push a tag that starts with `v`:

```bash
git tag v4.0.0-beta.1 && git push origin v4.0.0-beta.1
```

The workflow stamps that version and an increasing build number into the app. It then publishes a GitHub release with the installer (`games247-<version>-setup.exe`) and the update feed (`latest_release.json`, with MD5 and SHA-256 checksums).

**Release notes**: `RELEASE_NOTES.md` has a `## <version>` section for each release, newest first, with one `- ` line per change, written for players. Add the section before tagging. The workflow puts the sections (up to 20) into the update feed as `notes` and uses the release's own section as the GitHub release description (falling back to GitHub's generated notes, with a warning, if there isn't one). The update prompt (`GuiReleaseNotes`) lists the notes of each release from the one offered back to the installed version (all of them, up to 10 releases, for a build that isn't in the list), scrolled with up and down, with **Update** and **Later**. An older feed without `notes` gets the old prompt. **Tested** on macOS with a local test feed (`LOCAL_TESTING_FILE`). **Not tested yet**: the workflow step that builds the feed (PowerShell).

**Auto-update**: on Windows, games247 checks `https://github.com/epos247/games247/releases/latest/download/latest_release.json` at startup. When the release's build number is higher, it offers **Update**. That one press downloads the installer straight away, checks the MD5, runs it silently as soon as the download is done, closes games247, and the installer relaunches it (`GuiApplicationUpdater::startDownload`; *Try again* only shows after an error). The installer waits for games247.exe itself to exit, not just its window, so files such as FreeImage.dll aren't still in use when they're replaced; a games247 still running after 20 seconds is closed (`WaitForGames247` in `tools/windows/games247.nsi`). Users get no admin prompt and don't have to pick any files.

**Installer**: `tools/windows/games247.nsi`, a per-user install in `%LOCALAPPDATA%\Programs\games247`. It adds Start menu and desktop shortcuts and an Installed apps entry. Uninstalling keeps `%USERPROFILE%\.games247` (settings, saves, cores).

**Not done yet**: code signing. Unsigned installers show a "Windows protected your PC" SmartScreen warning (More info → Run anyway). The workflow has a `Sign` step ready for when there's a certificate.
